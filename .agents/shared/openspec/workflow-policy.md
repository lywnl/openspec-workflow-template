# 通用工作流规则

## 路径与版本

先确认用户所指的项目。`openspec context --json` 用于识别 CLI 解析的根；若根在授权范围外，停止对该根的读写并说明。不要默认使用全局 store。仅在用户明确选定 store 时携带该版本支持的 `--store` 参数。

使用 `openspec status --change <名称> --json` 和 `openspec instructions <产物> --change <名称> --json` 返回的 schema、依赖、实际路径与约束。首次确认接口、接口变化或命令异常时查 `--help` 和实际输出，不逐阶段反复查同一帮助。CLI 不提供 context 时，依据当前目录中已确认的 `openspec/` 与配置定位；不能在根仍不确定时写文件。

命令传入名称和路径时正确引用，文件名不应被解释为 shell 代码。自定义 schema 的产物按实际依赖图处理；机器证据助手仅支持单根普通文件和非空 UTF-8 Markdown checkbox 任务清单。其他格式先按 [核验方式](verification-evidence.md#核验方式) 选择适配路径，不强行改写项目 schema。

## 风险等级

| 等级 | 适用范围 | 规划和检查 |
| --- | --- | --- |
| `fast` | 低风险、可回滚的小修复或局部调整；不改变安全、数据模型和公共契约 | 简短规划与评审、聚焦真实验证；保留必需产物和风险相关证据 |
| `standard` | 常规单域功能或内部行为调整 | 完整需求映射、聚合规划评审、与改动相称的实现验收 |
| `strict` | 安全、权限、租户隔离、持久化迁移、不可逆操作、公共破坏性契约、多域事务或发布级风险 | 完整规划和来源追踪；独立规划评审、独立代码质量评审及高风险真实验收 |

用户可以要求更严格的等级。未明确时按事实判断，信息不足先用 standard；发现强制升级风险时停止相应实施，补足 strict 规划深度、评审和验收要求。

`workflow_profile` 是本模板在变更 `.openspec.yaml` 中维护的元数据，取值为 fast、standard 或 strict；schema、产物和依赖读取 CLI 实际结果，不能期待 status 自动返回本模板等级。review、apply、verify、archive 的报告和 `--profile` 均须与该字段一致；缺失时先评估登记，冲突或无效值先明确原因，不靠更换参数降低门槛。它不是 CLI 内置安全等级，`openspec validate --strict` 也不等于完成 strict 开发流程。

默认三个等级都使用 `spec-driven`，按实际依赖组织 proposal、specs、design、tasks；不能因 fast 而省略必需规格或设计。首次通过 `openspec schema which <名称> --json` 核实来源与可解析性，不能由本地 schemas 目录是否存在推断内置 schema 是否可用。复用未变化的查询结果；解析失败停止相关创建，不自动降级或 init。用户明确指定或已有项目采用其他 schema 时核对兼容性，冲突先说明并确认，不覆盖既有选择，不把流程冲突留作编码任务。

任务清单是实施依据，不默认增加另一份详细 writing plan。只将实现和具体测试、检查写成必需 checkbox；正式验收结论、验收指纹与归档写为交付条件，不能成为验收入口的循环前置任务。已有循环任务需明确修订并复审，不能直接勾选或静默删除。

fast 的规划评审和验收报告采用共享规则中的短格式，已有来源、命令及证据用引用承接，不重复抄写。机器指纹由助手生成，不另写同内容的手工清单；保留两个阶段的独立报告，避免后写验收内容使规划报告指纹失效。

fast 仍需真实验证和必要证据；“短格式”只减少叙述，不允许跳过需求覆盖、失败路径或项目规定的机器门禁。

## 入口与回退

### 根据意图选择入口

| 当前请求或状态 | 本模板的处理方式 |
| --- | --- |
| 需求不清楚、请点拨、头脑风暴或比较方案 | explore：先探索场景与行为，再讨论技术 |
| 新需求，要求一步一步推进 | new-change 建立骨架；后续 continue-change 默认完成一个就绪产物 |
| 新需求，明确要求一次完成全部规划 | new-change 后连续执行 continue-change，按依赖补齐全部必需规划，完成后提示 review-change；授权含评审时才执行 |
| 已有变更，补写或修改规划 | continue-change，不重复创建同名变更 |
| 规划齐备，检查是否可以实施 | review-change |
| 已有实现，检查是否满足需求和交付条件 | verify-change |

用户说“继续”“下一步”“生成下一份”时，默认只完成一个就绪规划产物后停止；一个 specs 产物可能含多个能力文件，应保持 schema 所需完整性并说明文件集合。即使这是最后一份规划，也不自动进入评审。只有用户明确要求持续完成的范围才连续推进，不把一次性规划授权扩大为评审、实施或归档。

`openspec-propose` 是另一套入口中一次创建变更并生成完整规划的技能，不属于本模板七个入口。未明确点名时，本模板用 new-change 与 continue-change 完成同等规划工作。用户明确指定原版 propose 时，核对其实际文件并说明差异，遵循该请求及其规划边界；已有项目的风险登记和规划评审要求仍须满足，不能生成完规划就宣称可直接实施。缺失技能时说明，不自动安装或编造调用。仅仅询问、引用或比较某个技能不构成执行该技能的请求。

若原版 propose 已生成规划，核对现有产物、补足风险元数据后仅提示 review-change，已有明确评审授权时才执行；需要修订时使用 continue-change，不能再运行 new-change。发现原版与定制入口混装时说明实际采用的路径；不自动删除、覆盖或重新初始化技能。

### 探索与规划交接

explore 是可选入口。需求已经明确时可以直接开始规划；没有探索文件不算缺少正式产物。后续规划应结合当前项目事实、正式规范和用户要求，不只依赖聊天记忆。

探索结论按含义区分，不要求每次回复都套用表格：

| 类别 | 后续处理 |
| --- | --- |
| 已确认需求 | 用户明确提出或接受的目标、行为、范围和约束，作为规划依据 |
| 候选建议 | 代理提出但未获确认的功能或方案，不自动写成必需需求或实施任务 |
| 已核实事实 | 记录相关代码、规范或配置来源；后续发现来源变化时重新核对，未核实推测不得归入事实 |
| 未决问题 | 标明影响、是否阻塞当前规划，以及后续解决阶段；不以默认值掩盖重大未知项 |

用户准备进入规划时，在对话中按需汇总以下内容，已有清晰摘要可直接复用，不重复输出：

```text
目标：
已确认的主要行为：
范围与非目标：
关键约束及事实来源：
候选方案与推荐理由：
未决问题及其影响：
```

摘要默认不落盘。用户要求或已有明确保存授权时，可保存探索笔记并登记为 proposal 来源；不要把整份笔记或聊天中的所有想法视为已确认。用户只要求讨论时，不因需求已清晰就自动创建变更。

new-change 承接已确认范围并核对现状，continue-change 将其按实际 schema 细化为正式规划。出现影响范围、可观察行为、兼容性、成本或验收的新决定时，针对该决定澄清；范围内的常规工程选择记录理由与假设，不逐项索要批准。已有正式产物时先读取当前文件，探索结论与其冲突需说明并处理，不能默默覆盖或将旧聊天当成更新的事实。

新信息只触发受影响决定及上下游产物的修订，不重启完整访谈。探索阶段未展开的实现细节可以在设计和任务中补全，规划来源和内容的实质性变化仍按既有评审与证据规则处理。

### 阶段约定

1. explore 可选，只调查与讨论；保存探索笔记应符合用户意图，不能暗中建立正式变更。
2. new-change 创建骨架、记录范围和等级，不自动编写全部规划。
3. continue-change 默认只生成下一个就绪产物后停止；用户要求完成全部规划时持续按依赖生成。规划齐备只提示评审，未经明确授权不自动评审。修订模式只改实际受影响内容。
4. review-change 判断规划是否可靠。PASS 可交给实施，PAUSE 需要解决或明确接受报告中的实质性警告，BLOCK 必须修正。
5. apply-change 需要明确实施意图。先完成必需产物、工程上下文与当前任务条件预检，再于首次任务修改前核验并登记实施开始。没有可推进任务时不提前登记；有效规划评审可复用，不机械重评。
6. verify-change 可在任务未完成时检查缺口并给出未通过结论；只有必需任务和真实验证均完成才登记验收通过，不能以规划得分或任务勾选代替运行结果。
7. archive-change 正常完成归档要求最新验收通过、必需任务完成、规范同步成功并校验；取消或放弃通过另一条明确路径记录。

### 两类评审的分工

review-change 回答“规划是否清楚、合理且可实施”，产物是规划评审与实施基线；verify-change 回答“当前实现是否符合规划，真实证据是否足够”，产物是实现验收与验收基线。二者不是两遍通用代码评审。

verify 核对规划指纹只为确认验收依据有效；规划及来源未实质变化时不重做规划评审。apply 已完成且仍有效的测试、需求映射和日志可供 verify 核对引用，不为切换入口再跑一遍。发现实现缺陷回 apply 再 verify；发现需求、设计或验收标准问题回 continue、review，再处理受影响实现。用户仅说“评审一下”时根据当前产物和关注对象选择；对象无法确定且会影响工作范围时再澄清。

CLI 状态中的产物完成字段和 `openspec validate --strict` 只证明其检查范围内的状态或格式；不能据此宣称规划语义评审、实现验收或独立代码评审通过。

## 文档与执行成本

- proposal 记录目的、范围、来源和影响；specs 记录可观察行为；design 记录技术决定；tasks 记录依赖、落点和验证。使用现有 Requirement、Scenario 名称和任务编号交叉引用，不复制整段需求或另建编号体系。
- 生成单个产物后检查其内容与实际依赖、复查状态即可。局部修订只核对受影响上下游；规划齐备进入评审前再做完整规划校验，不因切换入口重复同一轮校验。
- standard/strict 的详细验收映射维护在结构化清单，报告引用清单并说明真实结论、异常和限制。原始日志直接索引，不要求每个小任务另写报告；任务有真实证据后及时标记完成。
- 工具已承担的内容、哈希和状态检查不再用另一组命令重复。写入、移动或上下文中断后的关键边界仍按证据规则检查，不能用“提速”复用失效证据。
- 进度用简短中文说明发现、当前阶段和阻塞；最终回复给结论、关键文件和剩余问题。正常情况不逐条展示哈希、内部字段或重复解释每个命令；排错或用户明确要求时展开。

实现缺陷回到 apply；需求、设计或验收条件有问题回到 continue，再 review。证据对应的实现变化后重新评估受影响验证；存在不相关阻塞时继续可独立推进的授权工作。

仅生成规划的请求不授权编码；明确授权整条开发链路时可以按门槛连续推进，不为了切换技能重复询问。分支、提交、上线和外部操作另遵循已有授权。

## 独立评审与成本

- fast/standard 默认在当前执行上下文完成聚合检查，只有争议或实际跨域风险才增加独立评审。
- strict 由未撰写相应规划或代码的独立人员/执行上下文评审，记录评审者、基线、发现及处置；同一作者换个标题不算独立。
- 可用且获准时使用一个有明确边界的评审子代理，不递归分派。已有符合当前基线的独立评审可以复用。
- 无法满足必需的独立评审时保留阻塞并说明所需支持，不将其改成普通自查；继续其他独立工作。
- 来源追踪在 review-change 中统一收口。continue 发现来源冲突时即时记录，不强制每份产物前后重复完整来源评审。
- 专项技能只在任务需要且已安装时使用。工具缺失可采用等价实现方法；无法满足必需能力时必须说明，不能引用不存在的技能冒充执行。

## 用户与环境授权

复用用户明确给出的授权范围、目标和限制。规划 PASS 不授权迁移，测试许可不授权生产上线。对新增费用、外传数据、环境修改或破坏性操作，先准备具体可审查的操作与回退说明，再确认尚未覆盖的授权。

不为绕过环境阻塞私启中间件或切换到替代库。真实数据库、模型、上传等验收按实际项目的要求执行；本地单元测试可以使用替身，但不能据此声明真实集成通过。
