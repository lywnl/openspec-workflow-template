# 项目上下文发现

## 最小必要调查

按以下顺序读取与任务相关的事实，不全盘扫描用户文件：

1. 用户明确的项目、目标、授权边界，以及适用于目标路径的 AGENTS.md。
2. 项目 README、依赖清单、锁文件、构建入口、CI 和测试配置。
3. 当前改动涉及的模块、公共接口、调用方、邻近实现与测试。
4. 项目引用的工程规范、设计系统、数据库及发布约定；仅在路径获准且确实相关时继续读取。

无 Git 仓库的项目仍可规划、实施和验证，改用文件内容快照。存在 Git 时记录当前分支和相关已改文件，不擅自切分支、创建 worktree 或清理无关改动。

## 要得到的结论

| 内容 | 记录方式 |
| --- | --- |
| 项目与规划目录 | 实际根、变更路径、允许操作的目录 |
| 工程约束 | 规则来源与对本任务的影响，不复制整份规范 |
| 技术栈 | 由清单和代码确认；缺少实现的项目说明是新建或纯文档项目 |
| 验证入口 | 命令、工作目录、运行前提；未验证的命令标记待核实 |
| 环境边界 | 本地可运行项、需授权的真实服务或费用、不可用依赖 |
| 改动范围 | 实际模块与调用关系，已存在的用户修改及需要保留的行为 |

信息足够支撑当前步骤就开始，不为每个任务重复读取相同且未变化的文件。实现时若观察到变化，读取新的相关状态。

已在当前上下文读过的规则、schema 指令和依赖可复用；上下文缺失或文件已变化时重新读取必要部分。不以时间间隔证明内容有效，也不另建缓存管理系统。区分稳定约束与准备修改的参考代码，读过的文件不自动成为永久冻结的规划来源。

## 技术栈适配

不内置固定的包管理器、测试框架、端口、部署平台、业务前缀或数据库。优先使用项目已有脚本。例如项目使用 Maven 就遵循该项目 Maven 入口；使用 pnpm 就遵循其 workspace 命令，而不是把示例当成通用要求。

页面任务沿用已有设计系统；只有新增页面、整体布局或交互模式变化时，才需要完整页面设计与浏览器验证。局部行为修复运行对应的聚焦检查。

数据、权限、网络和持久化任务检查已有的隔离、事务、迁移、错误处理及配置所有者。不要因为引入本工作流就生成新服务、权限树、数据库或公共接口。

缺少专项技能时从项目代码、框架文档和已有测试建立等价方案。缺少规则不代表可以编造当前项目约定；所选的新约定应明确为建议，并与现有代码相容。

## 规划与源码分离

CLI 解析的规划根可能与源码根不同。报告中明确二者，不把 openspec 目录当成业务代码目录。每个证据路径记录所属根；跨根文件只有得到相应访问授权后才能读取。

附带证据助手只支持一个根，并拒绝输入范围内的符号链接。遇到多根源码或合法链接，采用 [人工核验步骤](manual-verification.md)：分别登记每个授权根的清单，复核原始文件后再汇总报告。复制一份来源快照不能证明外部原文件仍未变化；不得扩大根到用户主目录、删除链接或漏登记关联源码来迎合助手。

## 编码前输出

在首次实施或范围实质变化时，简要输出已确认的工程规则、实现位置、验证入口及待授权项。只有这些信息足以支撑当前任务时，才声明 `Pre-Code Context Gate: PASS`。
