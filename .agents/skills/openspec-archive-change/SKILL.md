# 同步规范与归档

读取 [工作流规则](../../shared/openspec/workflow-policy.md) 和 [归档与证据规则](../../shared/openspec/verification-evidence.md)。同步在当前流程内完成，不依赖另一个已安装技能。

## 确认归档类型

明确变更名称、CLI 解析的根和归档授权；多个候选时澄清，不猜测。默认是正常完成归档；只有用户明确要求取消、放弃或替代时使用取消路径。

## 正常完成

1. 检查是否已有同步检查点：有则按 [中断恢复规则](../../shared/openspec/verification-evidence.md#同步检查点与中断恢复) 使用 `archive_checkpoint.py check` 核对阶段和差异，不能当作首次归档重写记录。首次归档读取 schema 必需产物、任务、最新验收与独立评审结果；machine 执行 `check-verify`，manual 按共享步骤重新枚举并比较验收清单。
2. 必需任务未完成、验收非 Ready for Archive、证据缺失/失效或存在阻塞时停止正常归档，转回对应流程。不能用“确认仍要归档”绕过完成标准。
3. 获取当前规格指令，读取 CLI 确定的增量规范和对应正式规范。若 schema 没有增量规格，明确记录无需同步。
4. 汇总将新增、修改、删除或重命名的要求，提前确认归档目标不存在。已有授权覆盖此次同步时继续；出现未约定的冲突或新增影响时先澄清。有规范同步时先运行 `archive_checkpoint.py prepare`，再写入预期内容。
5. 按要求合并，保留不相关内容；标准 spec-driven 主规范采用 `## Requirements`，自定义 schema 遵循其明确的同步规则。不要直接复制增量文件覆盖正式规范；存在规则冲突时停止受影响同步。
6. 运行 CLI 支持的规范校验，例如 `openspec validate --specs --strict --no-interactive`，并逐项比较变更要求已落实。同步或校验失败时不移动变更，报告已修改文件及剩余差异。
7. 规范符合预期且校验通过后运行 `archive_checkpoint.py synced`。在 `reports/archive-record.md` 记录核验方式、验收核验、检查点引用、校验结果和非阻塞限制。无增量规范时仅写无需同步与验收依据，不创建空检查点。同步以外的代码、规划或证据变化仍需重新核验。
8. 按 CLI 解析的 changes 根建立 archive，目标为 `YYYY-MM-DD-<变更名>`；原名已有日期前缀时不重复添加。目标存在就停止，不覆盖。
9. 按共享恢复规则确认非同步输入仍有效、规范符合预期，再整体移动变更目录，保留 `.openspec.yaml`、评审和证据；验证目标存在、原活动目录已移除、主规范正确，然后以归档目录为 `--change` 运行 `archive_checkpoint.py archived`，补记最终路径与完成状态。

不要在已经手动同步后盲目再次执行会重复同步的 CLI archive 命令。选择一种明确的归档机制，遵循当前 CLI 支持的参数。

## 取消或放弃

记录 `Cancelled` 或 `Superseded`、原因、未完成任务、残留代码及环境状态。不得同步未完成增量为正式规范；如果以前已经同步过，记录差异并单独处理，不自动反向删除。

在用户授权下移动到 archive 并保留取消记录。取消不授权回滚业务代码、删除数据或清理环境，不要求伪造通过验收。

## 输出

报告归档类型、实际路径、规范同步状态、验收基线及残留事项。正常完成、取消和部分同步失败必须明确区分。归档本身不执行 Git 提交、合并、推送或部署。
